## Context

A PDUFA date is the FDA's target action date for an application; advisory committee meetings and expected topline readouts are the other scheduled binary events in biotech. The 2026-10-07 edge feasibility audit wants them as a free company-level source (row 9) and for sizing: no hold through a known binary date unless the strategy is that event (row 12).

There is no free machine-readable FDA feed of PDUFA dates; companies disclose them in press releases, 10-Qs and 10-Ks, and revise them (a major amendment typically extends the date by three months). Advisory committee meetings are published in the Federal Register (separate spec, `specs/fda-advisory-committee-connector.md`, which writes into this calendar).

What exists or is specified:
- `specs/portfolio-and-risk.md` `BinaryEventGuard` reads a manually maintained `config/catalysts/upcoming.yaml` and lists a "catalyst calendar auto-feed" as out of scope. This spec is that feed.
- core-hub is the sole writer to Postgres (Invariant 2); Flyway scripts create the schema on an empty database.
- The extraction schema is a Pydantic model mirrored field-for-field by a Java record, with a generated contract fixture (Invariant 7).

## What this builds

1. **Extraction fields** (additive, minor schema version): a signal may carry zero or more `catalysts`, each `{catalyst_type: pdufa | adcomm | topline_expected, catalyst_date, date_precision: day | month | quarter | half, application_id (nullable), status: scheduled | extended | met | missed | withdrawn}`. Prompt version bumped; golden set gains labelled catalyst examples; contract fixture regenerated by pytest.
2. **`catalyst` table** (`V<n>__catalyst_calendar.sql`): one row per disclosure, natural key `(program_key, catalyst_type, disclosed_event_id)`, append-only (`DO NOTHING`), with `disclosed_at` = the disclosing signal's `published_date`. A revision is a new row; nothing is updated.
3. **As-of view**: for `(program_key, catalyst_type)`, the effective catalyst on date D is the latest row with `disclosed_at ≤ D`. `GET /api/v1/catalysts?ticker=&from=&to=&as_of=` returns effective catalysts, parameterized and allowlist-validated like the existing endpoints.
4. **Guard integration contract**: `BinaryEventGuard` reads this endpoint (with `as_of` = the decision's known-at time) instead of `upcoming.yaml`; the YAML stays as a manual override merged on top. The guard change itself is made in the portfolio-and-risk spec; this spec provides and documents the endpoint.

## Out of scope

- Advisory committee notices (`specs/fda-advisory-committee-connector.md`).
- Hypotheses on catalysts (for example pre-PDUFA run-up), registered separately.
- Implementing `BinaryEventGuard`.
- Paid catalyst calendars.

## Constraints

- Invariant 7: Python model, Java record and the generated fixture change together; `FAIL_ON_UNKNOWN_PROPERTIES=false` keeps older consumers working.
- Invariant 10: declared natural key above; add it to requirements §3.7's table.
- Invariant 12: parameterized queries; injection tests on the new endpoint.
- Invariant 14: `event_id` unchanged by the schema bump; re-extraction creates new `extraction_id`s only.
- Point-in-time: a catalyst is known from its disclosing document's `published_date`, never from the catalyst date and never from a later revision.
- `date_precision` matters: "PDUFA in the second half of 2026" must not become 2026-07-01.
