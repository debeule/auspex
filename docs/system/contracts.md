## Scope

Everything that crosses a process boundary on Kafka: what each topic carries and who produces and consumes it, message keys, the shape of the raw pointer, the signal event and the corroborated event, identity formulas, closed value sets, schema versioning, the declared natural keys of the Kafka-fed store paths, and dead-letter topic naming, partitioning and headers.

Values live in their machine authorities, not here (see below). Not in this file: which failures a consumer dead-letters, its retries, its pause and replay, and its reaction to an invalid record ([consumption.md](../core-hub/consumption.md)); write behaviour once a record is consumed, including the store types of `confidence_score` and how `signal_current.source_type` is set ([storage.md](../core-hub/storage.md)); re-extraction ([extraction.md](../ingestion/extraction.md)); what logs carry ([observability.md](../operations/observability.md)).

## Requirements

- <a id="CON-001"></a>**CON-001** — Kafka topics are provisioned only from `docker/topics.yaml`, by the `kafka-init` one-shot, never as a side effect of constructing a producer or consumer.
- <a id="CON-002"></a>**CON-002** — Topic roles: `auspex.raw.ingested` carries raw-document pointers from the scraper to core-hub's raw audit; `auspex.signals.extracted` carries `ResearchSignalEvent` from the scraper to core-hub; `auspex.signals.corroborated` carries `CorroboratedSignalEvent` from core-hub to the strategy runtime. Each of the three has a dead-letter topic `<topic>.dlt`. Partition counts and retention are values in `docker/topics.yaml`.
- <a id="CON-003"></a>**CON-003** — Message keys are document identity: a raw pointer is keyed by `external_id`, a signal event by `event_id`, a corroborated event by `entity_key`. No topic is keyed by a gene target.
- <a id="CON-004"></a>**CON-004** — Every dead-letter topic has the same partition count as its source topic. This is defence in depth: the dead-letter publish lets the producer choose the partition (CON-036), so it does not depend on the counts matching.
- <a id="CON-005"></a>**CON-005** — A raw pointer is the `RawDocument` fields in snake_case without `raw_content`, plus `raw_object_key` (the archive object's key), keyed by `external_id`, with a `schema_version` header. Its time field is `retrieved_at`. Producer and consumer read the same field names: the consumer requires `raw_object_key`, `source_type`, `external_id`, `content_sha256` and `retrieved_at`, the last with an offset.
- <a id="CON-006"></a>**CON-006** — A raw pointer is published for every document the archive writes, whether or not it yields a signal: right after the archive write, before the prefilter, the processed-marker check and extraction. A fetch whose archive object already exists publishes no new pointer, because the pointer was sent when that object was written.
- <a id="CON-007"></a>**CON-007** — The raw pointer has a fixture generated by pytest from the producer's real output, `raw_pointer_v1.json` in the core-hub contract test resources, which the core-hub tests read. A committed file that differs from the generated one fails the generating test.
- <a id="CON-008"></a>**CON-008** — The fields of `ResearchSignalEvent` are those of the Pydantic model in `services/ingestion-scraper/src/auspex_ingest/models.py`, in snake_case on the wire through an explicit snake-case naming strategy, and the Java record matches them field for field. `external_id` and `raw_object_key` are on every event, keeping the chain of custody to the audit row and the archived document. List fields (`gene_targets` among them) are lists, never a single value. Only `canonical_id` and `primary_company` may be null.
- <a id="CON-009"></a>**CON-009** — The signal fixture `signal_event_v1.json` is generated by `services/ingestion-scraper/tests/unit/test_contract_fixture.py` from the Pydantic model and is never edited by hand; CI regenerates it and fails when the committed contract fixtures differ.
- <a id="CON-010"></a>**CON-010** — A field present on one side of a contract and missing on the other fails a test on that side.
- <a id="CON-011"></a>**CON-011** — Every timestamp on the wire is ISO-8601 in UTC with a `Z` suffix; a naive timestamp is invalid on the wire. The producer refuses a naive datetime and converts an aware one to UTC before serializing.
- <a id="CON-012"></a>**CON-012** — `confidence_score` is required and is a number in [0.0, 1.0], both ends included. The producer never clamps or rescales it. Java holds it as a non-null `BigDecimal` bounded to that range, never as a primitive `double`.
- <a id="CON-013"></a>**CON-013** — `event_type` takes only the values of the `EventType` literal in `services/ingestion-scraper/src/auspex_ingest/extractor.py`. The producer records a model label outside that set as `other`.
- <a id="CON-014"></a>**CON-014** — `source_type` takes only the names of the entries in `services/ingestion-scraper/config/sources.yaml`.
- <a id="CON-015"></a>**CON-015** — `directionality` is one of `positive`, `negative`, `neutral`.
- <a id="CON-016"></a>**CON-016** — Each `trial_ids` entry is `NCT` followed by eight digits.
- <a id="CON-017"></a>**CON-017** — The closed-set fields `source_type`, `directionality` and `event_type` carry only values from their sets (CON-013 to CON-015); a value outside its set is invalid on the wire. How a consumer reacts to an invalid value is in [consumption.md](../core-hub/consumption.md).
- <a id="CON-018"></a>**CON-018** — `event_id = uuid5(NAMESPACE_URL, canonical_id)` when `canonical_id` is set, else `uuid5(NAMESPACE_URL, "<source_type>:<external_id>")`. Applies INV-14.
- <a id="CON-019"></a>**CON-019** — `extraction_id = uuid5(NAMESPACE_URL, "<event_id>:<schema_version>:<prompt_version>:<prefilter_version>:<extraction_model>")`.
- <a id="CON-020"></a>**CON-020** — `canonical_id`, when set, starts with one of the type prefixes in `_CANONICAL_PREFIXES` (`services/ingestion-scraper/src/auspex_ingest/models.py`). A connector that can supply a canonical id supplies it for every document, or fails.
- <a id="CON-021"></a>**CON-021** — `raw_fetch_audit` is keyed by the MinIO object key; a second insert of the same key does nothing (append-only). Applies INV-10.
- <a id="CON-022"></a>**CON-022** — `signal_current` is keyed by `event_id`; a later extraction of the same event updates the row (latest extraction wins).
- <a id="CON-023"></a>**CON-023** — `signal_extraction_history` is keyed by `(event_id, extraction_id)`; a repeated pair does nothing (append-only).
- <a id="CON-024"></a>**CON-024** — `source_observation` is keyed by `(event_id, source_type, external_id)`; a repeated triple does nothing (append-only).
- <a id="CON-025"></a>**CON-025** — `corroboration` is keyed by `(entity_key, participants_hash)`; a repeated pair does nothing, and a larger participant set for the same entity supersedes the smaller one rather than duplicating it.
- <a id="CON-026"></a>**CON-026** — A `(:Signal)` node is merged on `event_id`.
- <a id="CON-027"></a>**CON-027** — Entity nodes are merged on their natural key, as the graph model in [storage.md](../core-hub/storage.md) declares it.
- <a id="CON-028"></a>**CON-028** — `schema_version` is `major.minor`, and the two parts are compared as integers, never as text. The current value is `EVENT_SCHEMA_VERSION` in `services/ingestion-scraper/src/auspex_ingest/models.py`. A record with an unknown major is incompatible; how a consumer reacts is in [consumption.md](../core-hub/consumption.md).
- <a id="CON-029"></a>**CON-029** — A record with a known major and another minor is compatible: the consumer accepts it, logs the version, and ignores properties it does not know.
- <a id="CON-030"></a>**CON-030** — `schema_version` travels both as a UTF-8 Kafka header and as a field of the record; consumers read the field.
- <a id="CON-031"></a>**CON-031** — A schema change updates the Pydantic model, the Java record and the regenerated fixture in one PR.
- <a id="CON-032"></a>**CON-032** — `CorroboratedSignalEvent` is snake_case JSON with ISO-8601 timestamps and no type header, its fields those of the Java record, and it is published only for corroborations that are not superseded.
- <a id="CON-033"></a>**CON-033** — A corroborated event is delivered at least once: core-hub sends it before the scan's commit, so a failed commit can send it again. Consumers treat `(entity_key, participants_hash)` as its identity.
- <a id="CON-034"></a>**CON-034** — The corroborated event carries `schema_version` and has a generated fixture that the Python consumer's tests read.
- <a id="CON-035"></a>**CON-035** — A dead letter goes to `<source topic>.dlt`, with the suffix in lowercase.
- <a id="CON-036"></a>**CON-036** — The dead-letter publish names partition `-1`, so the producer chooses the partition.
- <a id="CON-037"></a>**CON-037** — A dead letter keeps the original record's key and carries the headers `kafka_dlt-exception-message` and `kafka_dlt-original-topic`. Its value is the original bytes when deserialization failed, and otherwise the record as snake_case JSON.

## Known traps

Sources: `CLAUDE.md:205`, `CLAUDE.md:209`, `CLAUDE.md:210`, `services/core-hub/CLAUDE.md:48-50`.

- **`DeadLetterPublishingRecoverer` defaults to an uppercase `.DLT` suffix and the source record's partition number.** The lowercase names need a custom resolver, and it returns partition `-1` (CON-035, CON-036). With the default, a dead-letter topic with fewer partitions than its source makes the publish fail. Confirmed for Spring Kafka 4.1 by `## 2026-08-16 — Step 1.3 — VERIFIED — DeadLetterPublishingRecoverer with Spring Kafka 4.1`.
- **A primitive `double` cannot be null.** A missing `confidence_score` would deserialize to `0.0` and pass validation, so Java holds it as a non-null `BigDecimal` (CON-012). The Postgres and Neo4j types are in [storage.md](../core-hub/storage.md).
- **Jackson's `FAIL_ON_UNKNOWN_PROPERTIES` must be `false` on the consumer**, or the first additive schema change makes every record unreadable (CON-029). The same setting is why the Java side cannot catch a field it lacks (CON-010).

## Rationale

Non-normative.

- **Keys are identity** (requirements §2). Keying on a gene target is impossible for the raw pointer, which is published before extraction runs, and nothing reads by gene target from a partition: corroboration is a graph query.
- **Near-miss identity formulas** (requirements §10.1). Keying on `(source_type, external_id, schema_version)` changes every id on a schema bump and duplicates every corroboration. Writing `uuid5` over `"<source_type>:<canonical_id or external_id>"` cannot collapse one document seen by two sources, because `source_type` differs. CON-018 avoids both.
- **Chain of custody** (requirements §10.2). Without `external_id` and `raw_object_key` a signal cannot be joined to its audit row, re-extracted from its archived document, or resolved back to its per-source dates.
- **Fixture name.** Requirements §13 names the generated fixture `research_signal_event.json`; the file has always been `signal_event_v1.json`, and CON-009 names it.
