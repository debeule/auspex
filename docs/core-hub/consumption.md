# Consumption

## Scope

What core-hub does between polling a record from `auspex.signals.extracted` or `auspex.raw.ingested` and acknowledging it or dead-lettering it: listener settings, deserialization, which failures dead-letter at once and which are retried, pausing while a store is down, counting dead letters, and replaying them. This file is the only owner of failure classification.

Not in this file: topic roles, dead-letter topic naming, partition and headers, and the wire values a failure class refers to (timestamps, `confidence_score`, closed sets, `schema_version`), all in [contracts.md](../system/contracts.md); what the stores hold and in what order they are written ([storage.md](storage.md)); the replay endpoint's authentication ([http-api.md](http-api.md)); the log format, what a log line may carry, and metric names ([observability.md](../operations/observability.md)).

## Requirements

- <a id="HUB-001"></a>**HUB-001** — core-hub consumes with two listeners, each in its own consumer group: `corehub-signal` on `auspex.signals.extracted` and `corehub-raw` on `auspex.raw.ingested`. Both start from the earliest offset when their group has none, never auto-commit, and poll at most as many records as finish well inside the poll interval (`max.poll.records`, a value in `KafkaConfig.java`).
- <a id="HUB-002"></a>**HUB-002** — On both listeners an `ErrorHandlingDeserializer` wraps the value deserializer, so a payload that cannot be deserialized reaches the error handler instead of failing inside the poll loop.
- <a id="HUB-003"></a>**HUB-003** — The signal listener ignores JSON properties it does not know (`FAIL_ON_UNKNOWN_PROPERTIES` is `false`), so a record of a known major version and a newer minor is accepted (CON-029).
- <a id="HUB-004"></a>**HUB-004** — A signal record whose value is not valid JSON goes to the DLT at once, without a retry.
- <a id="HUB-005"></a>**HUB-005** — A signal record carrying a timestamp without an offset (CON-011) goes to the DLT at once, without a retry.
- <a id="HUB-006"></a>**HUB-006** — A signal record whose `schema_version` has a major version core-hub does not know (CON-028) goes to the DLT at once, without a retry.
- <a id="HUB-007"></a>**HUB-007** — A signal record without a `confidence_score` goes to the DLT at once, without a retry; a missing score is never read as zero (CON-012).
- <a id="HUB-008"></a>**HUB-008** — A signal record whose `confidence_score` lies outside [0.0, 1.0] goes to the DLT at once, without a retry; the score is never clamped or rescaled.
- <a id="HUB-009"></a>**HUB-009** — A signal record whose `source_type`, `directionality` or `event_type` is outside its closed set (CON-013 to CON-017) goes to the DLT at once, without a retry.
- <a id="HUB-010"></a>**HUB-010** — A raw pointer that is not a JSON object, lacks a field CON-005 requires, or has a `retrieved_at` without an offset goes to the DLT at once, without a retry.
- <a id="HUB-011"></a>**HUB-011** — The signal listener validates its payload (`@Valid`) with a validator registered on the listener endpoint, so the bean constraints of the signal record run on every consumed record.
- <a id="HUB-012"></a>**HUB-012** — Every other failure is transient: the record gets one attempt and two retries, waiting 5 s and then 30 s by default (`auspex.kafka.retry.*` in `application.yml`), and then goes to its DLT. A failing record never blocks its partition (applies INV-11).
- <a id="HUB-013"></a>**HUB-013** — While Postgres or Neo4j does not answer, both listener containers are paused; they resume only when both stores answer. The probe interval is a value in `application.yml` (`auspex.kafka.store-check-interval-ms`).
- <a id="HUB-014"></a>**HUB-014** — A record's offset is committed only after both stores have returned for that record, one record at a time (`ack-mode: RECORD`).
- <a id="HUB-015"></a>**HUB-015** — Every dead-lettered record is counted by its source topic, whatever its failure class. The metric's name is in [observability.md](../operations/observability.md).
- <a id="HUB-016"></a>**HUB-016** — `POST /api/dlt/{topic}/replay`, for `auspex.signals.extracted.dlt` or `auspex.raw.ingested.dlt`, re-publishes that dead-letter topic's records to the source topic named in each record's `kafka_dlt-original-topic` header, with the original key and value, and commits its position after each record in consumer group `corehub-dlt-replay`, so a later call does not replay a committed record. Any other topic is 404. The listeners then store the records as on first delivery. Who may call it: [http-api.md](http-api.md).
- <a id="HUB-017"></a>**HUB-017** — A replay covers only the records on the dead-letter topic when the call starts; later ones wait for the next call. It drops the `kafka_dlt-*` headers and serializer type headers and keeps the record's other headers. Delivery is at-least-once: a crash between a send and its commit replays that record again, and the idempotent writes of [storage.md](storage.md) absorb the duplicate.
- <a id="HUB-018"></a>**HUB-018** — While the signal listener handles a record, its log lines carry the record's `event_id` and `source_type` in the MDC (`auspex.event_id`, `auspex.source_type`), and the listener clears the MDC when the record is done. The log format and what a line may carry are the log contract in [observability.md](../operations/observability.md).

## Known traps

Sources: `CLAUDE.md:204`, `services/core-hub/CLAUDE.md:47`, requirements §10.3.

- **Without `ErrorHandlingDeserializer` a malformed payload never reaches the error handler.** It fails inside the poll loop before any handler runs, and the container retries the same offset forever (HUB-002).
- **`@Valid` on a `@KafkaListener` parameter does nothing by itself.** Bean validation runs on listener arguments only with a validator registered on the endpoint registrar (HUB-011).
- **`spring.kafka.listener.*` properties configure the factory Spring Boot builds.** Both listener factories here are built by hand in `KafkaConfig.java`, so a property set in `application.yml` may not reach them (HUB-014).

## Rationale

Non-normative.

- **Pause rather than more retries.** A Postgres or Neo4j restart outlasts a short back-off, and every record consumed meanwhile would be dead-lettered. Pausing holds records on the topic; the three deliveries stay as §3 rule 10 sets them (`2026-10-09 — Soak-test readiness — CHOICE — transient Kafka failures pause instead of retrying longer`).
- **Replay is at-least-once, not at most once.** The replay commits each record's offset after its send is acknowledged, so a crash in between sends the record again. The archived spec and the service README say "at most once"; the writes are idempotent, so the duplicate is harmless (HUB-017).
