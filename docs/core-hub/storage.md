## Scope

What core-hub writes to Postgres and Neo4j once a record is consumed: schema ownership, write order, idempotency, the graph model, company tickers, edge replacement, the raw audit, and the single-user schema. core-hub is the only writer of both stores ([INV-2](../system/invariants.md#INV-2)); the one exception, writes into empty stores by the restore one-shot, is written only under [INV-2](../system/invariants.md#INV-2).

Not in this file: the natural key of each store path (CON-021 to CON-027 in [contracts.md](../system/contracts.md)); when a record is acknowledged or dead-lettered ([consumption.md](consumption.md)); the corroboration record and the pending flag the scan reads ([corroboration.md](corroboration.md)).

## Requirements

- <a id="HUB-019"></a>**HUB-019** — Flyway owns the Postgres schema: the migrations in `services/core-hub/src/main/resources/db/migration/` create it, and Hibernate runs with `ddl-auto: validate`, never `update` or `create`.
- <a id="HUB-020"></a>**HUB-020** — An applied migration is never edited, comments included: Flyway validates the checksum of every applied script at startup, and a change is a new migration with the next free version.
- <a id="HUB-021"></a>**HUB-021** — The migrations apply to an empty database; there is no legacy schema to migrate from (SYS-003).
- <a id="HUB-022"></a>**HUB-022** — Every write path is idempotent on the natural key that CON-021 to CON-027 declare for it (applies INV-10), so a redelivered or replayed record leaves the stores as its first delivery did.
- <a id="HUB-023"></a>**HUB-023** — `Signal` nodes, entity nodes and their relationships are written with `MERGE`, never `CREATE`.
- <a id="HUB-024"></a>**HUB-024** — Each signal record is written to Neo4j first, then to Postgres, and is acknowledged only after both have returned (HUB-014).
- <a id="HUB-025"></a>**HUB-025** — A record that dead-letters after its Neo4j write leaves a `Signal` node with no Postgres rows; its redelivery or replay makes the two stores agree, and nothing else repairs the graph.
- <a id="HUB-026"></a>**HUB-026** — Every `@Transactional` names its transaction manager, `jpaTransactionManager` or `neo4jTransactionManager`.
- <a id="HUB-027"></a>**HUB-027** — SQL and Cypher bind every value as a parameter (applies INV-12): an ArchUnit rule forbids raw `Statement` calls in the `signal`, `corroboration`, `audit`, `query` and `health` packages, and behavioural injection tests cover the REST boundary.
- <a id="HUB-028"></a>**HUB-028** — In `signal_current`, `source_type`, `external_id` and `canonical_id` are set by the event's first observation and never changed by a later one; every observation appends a `source_observation` row.
- <a id="HUB-029"></a>**HUB-029** — `confidence_score` is `NUMERIC(4,3)` in Postgres and a `double` property in Neo4j, converted explicitly before the graph write so that Cypher compares it as a number. Its wire type is CON-012.
- <a id="HUB-030"></a>**HUB-030** — The graph holds `(:Signal)` nodes keyed on `event_id` and carrying the event's scalar fields, and entity nodes `(:GeneTarget {name})`, `(:Mechanism {name})` and `(:Company {name, ticker})`. A signal is a node, never a set of relationship properties.
- <a id="HUB-031"></a>**HUB-031** — The only relationships written are `(:Signal)-[:TARGETS]->(:GeneTarget)`, `(:Signal)-[:USES_MECHANISM]->(:Mechanism)` and `(:Signal)-[:MENTIONS]->(:Company)`.
- <a id="HUB-032"></a>**HUB-032** — On every start, `Neo4jSchemaInitializer` creates, where absent, unique constraints on `Signal.event_id`, `GeneTarget.name`, `Mechanism.name` and `Company.name`, indexes on `Signal.published_date`, `Signal.source_type`, `Signal.corroboration_pending` and `Company.ticker`, and one `(:GraphSchema {version})` node.
- <a id="HUB-033"></a>**HUB-033** — The company-level fields `event_type`, `primary_company`, `program_identifiers` and `trial_ids` are stored in `signal_current` only, not in the graph.
- <a id="HUB-034"></a>**HUB-034** — A `Company` node merges on its `name` as extracted, never on `ticker`. Its `ticker` is set only when exactly one SEC ticker matches the normalized name; a later merge without a single match never clears it; and adding a ticker to the watchlist sets it on the companies that match that ticker's SEC title and have no ticker yet.
- <a id="HUB-035"></a>**HUB-035** — Matching a company name to an SEC title compares normalized forms: lower-cased, apostrophes and periods removed, other punctuation turned into spaces, and trailing corporate suffixes dropped (`CompanyNameNormalizer`).
- <a id="HUB-036"></a>**HUB-036** — A signal whose companies carry no ticker is stored and corroborated like any other and stays reachable through its gene targets and mechanisms; a ticker-keyed response ([http-api.md](http-api.md)) includes it only through a company that carries that ticker.
- <a id="HUB-037"></a>**HUB-037** — A write replaces the signal's own entity edges: in the same transaction it deletes each `TARGETS`, `USES_MECHANISM` and `MENTIONS` edge whose entity the event no longer lists. Entity nodes, and other signals' edges to them, stay.
- <a id="HUB-038"></a>**HUB-038** — Each raw pointer inserts one `raw_fetch_audit` row keyed on its MinIO object key (`raw_object_key`), holding the pointer's `source_type`, `external_id`, `content_sha256` and `retrieved_at` (CON-005, CON-021).
- <a id="HUB-039"></a>**HUB-039** — The schema is single-user: no table carries a `user_id`, and the multi-user path is one migration, described in the comment of `V3__watchlist_schema.sql` (SYS-004).

## Known traps

Sources: `CLAUDE.md:207`, `CLAUDE.md:208`, requirements §9, `services/core-hub/src/main/resources/db/migration/V4__company_level_fields.sql`.

- **`MERGE (c:Company {ticker: null})` matches every company without a ticker.** Most extracted companies have none, so merging on `ticker` would collapse unrelated companies into one node, and Neo4j's uniqueness constraints, which ignore nulls, would not catch it. `Company` merges on `name` (HUB-034).
- **Neo4j has no decimal type.** A `BigDecimal` written as is may be stored as a string, and Cypher comparisons on it then fail silently. The score is written as `double` (HUB-029).
- **The `V4` migration's header comment says "schema 1.1".** The event schema is 1.0 (CON-028); the comment is frozen with the applied script (HUB-020) and is not a statement of the current version.

## Rationale

Non-normative.

- **The signal is a node** (requirements §14, settled). Corroboration needs a signal that several entity nodes point back to; as relationship properties it would be copied onto every edge.
- **The graph-only `Signal`** (HUB-025). The two stores are written in sequence without an outbox; a record that fails after the graph write is retried and, if it dead-letters, leaves the node behind until it is replayed. The node is marked pending, so the scan may use it before Postgres has its row.
- **No `VIA` migration.** The writer emits `USES_MECHANISM` and the ArchUnit rule of HUB-031 keeps it so; no stack ever held `VIA` edges (`2026-10-09 — Graph and connector wiring fixes — CHOICE — no VIA migration`).
- **Retired repository rule** (HUB-040). core-hub uses `JdbcTemplate` and the Neo4j `Driver` directly; it has no Spring Data repositories to separate.
