# Corroboration

## Scope

How core-hub finds corroborations: the `CorroborationService` extension point and its contract test, the entity rules file and canonical keys, broad entities, independent sources, the only corroboration kind, the episode and its record, ticker records, the rules sync, the pending-signal scan, the publication of new records, the score, and the scan's failure counter.

Not in this file: the shape, versioning and delivery identity of the published `CorroboratedSignalEvent` (CON-032 to CON-034 in [contracts.md](../system/contracts.md)); the graph the scan reads ([storage.md](storage.md)); how REST responses present corroborations ([http-api.md](http-api.md)); the quality gate on sampled corroborations, which [extraction.md](../ingestion/extraction.md) owns; metric names ([observability.md](../operations/observability.md)).

## Requirements

- <a id="COR-001"></a>**COR-001** — All corroboration sits behind `CorroborationService` (applies INV-5). Every implementation extends the abstract `CorroborationServiceContractTest` and passes it unmodified; the test's helpers write signals as the write path does, pending with a write token (COR-008).
- <a id="COR-002"></a>**COR-002** — The implementation is `ScheduledCorroborationService`, a scan of the graph on a fixed delay set in configuration (`corroboration.interval-ms`). A stream-processing implementation is not a requirement; one would replace this one behind the same interface.
- <a id="COR-004"></a>**COR-004** — The only corroboration kind is shared-entity corroboration over `GeneTarget` and `Mechanism` nodes. Its `entity_key` is the entity's canonical key (COR-015), a colon, and the node label, for example `BCL11A:GeneTarget`. A new kind is a change to this requirement, made by the spec that adds it.
- <a id="COR-006"></a>**COR-006** — A record's `first_detected_at` is the time of the scan that wrote it and is diagnostic only; nothing joins or filters on it.
- <a id="COR-008"></a>**COR-008** — Every graph write of a signal marks it pending (`corroboration_pending`) with a fresh `write_token`, in the write's own transaction. The rules sync (COR-020) also marks every signal pending.
- <a id="COR-009"></a>**COR-009** — A scan reads at most one batch of pending signals published no later than its start (`corroboration.scan-batch-size` in `application.yml`) and reconciles every entity a pending signal touches: the entities it links to now and the `entity_key` of every live row that lists it, so an entity a re-extraction dropped is reconciled too. An entity with more eligible signals than the degree cap (`corroboration.degree-cap`, default 500) is skipped.
- <a id="COR-010"></a>**COR-010** — A scan's inserts commit only after every event it sends is acknowledged; the pending flags it read are cleared after that commit, and only on signals whose write token is still the one the scan read. A failed send, commit or clear leaves the signals pending for the next scan.
- <a id="COR-011"></a>**COR-011** — The only clock a scan applies is a signal's own `published_date`: a signal dated after the scan's start stays pending, takes part in nothing and is read by the first scan after its date. Otherwise no clock decides which signals a scan sees: a write that commits late, a lagging partition, a dead-letter replay and a re-extraction are all scanned once committed.
- <a id="COR-012"></a>**COR-012** — Each live row with no `excluded_reason` and no `published_at` is sent to `auspex.signals.corroborated`, keyed by `entity_key`, and its `published_at` is set in the scan's transaction: a joining signal publishes the episode's new record once, an excluded record is never sent, and a record that stops being excluded is sent then. A commit that fails after its sends were acknowledged sends the event again on the next scan, so delivery is at-least-once (CON-033).
- <a id="COR-013"></a>**COR-013** — A corroboration's score is `0.7 × diversity + 0.3 × recency`, clamped to [0, 1], where `diversity = min(1, (distinct_source_count − 1) / 4)` and `recency` falls linearly from 1 at `corroborated_at` to 0 ninety days later. The score is computed when it is read, against the service clock, and is never stored or published.
- <a id="COR-014"></a>**COR-014** — Every failed run, whether the scan, a send or the clear failed, increments the scan-failure counter, whose name is in [observability.md](../operations/observability.md).
- <a id="COR-015"></a>**COR-015** — One rules file, `config/corroboration/entity-rules.yaml`, read at start from `corroboration.rules-file`, defines which entity names are one entity (`synonyms`), which entities are too broad to corroborate (`excluded`) and which participants are one finding (`same_finding`). An entity's canonical key is, for a `GeneTarget`, its name after Unicode NFKC, upper-cased, with every character that is not a letter or digit removed; for a `Mechanism`, after NFKC, lower-cased, with every run of other characters turned into one space and trimmed; a key listed as a variant is then replaced by its canonical key. core-hub refuses to start when the file is missing or invalid: a name not in canonical form, a variant under two canonical keys, a canonical key that is also a variant, an excluded name that is a variant, a source type outside CON-013, or a title threshold outside (0, 1]. The rules hash is the SHA-256 of the file's bytes. Each `GeneTarget` and `Mechanism` node carries its `corroboration_key`; two nodes with one key and one label are one entity.
- <a id="COR-016"></a>**COR-016** — An entity is broad when, and only when, its canonical key is in `excluded` for its label. A broad entity's records are stored with `excluded_reason` `broad_entity`, never published, and it gets no ticker record (COR-019).
- <a id="COR-017"></a>**COR-017** — Two participants are the same finding when their `source_type`s form a pair listed in `same_finding.source_type_pairs`, both have a title, and the Jaccard overlap of their title token sets (titles through the `Mechanism` normalisation of COR-015, split on spaces) is at least `title_token_jaccard_min`. Two participants are independent when their `source_type`s differ and they are not the same finding. `distinct_source_count` is the largest number of participants that can be chosen so that every two are independent; a set corroborates when it is at least 2.
- <a id="COR-018"></a>**COR-018** — Signals reach an entity through `TARGETS` or `USES_MECHANISM`, never `MENTIONS`. An episode is built on a scope, the entity's eligible signals (published no later than the scan's start) or those of them that mention one ticker (COR-019), by replaying them in `(published_date, event_id)` order: a signal published no later than 90 days, both ends included, after an open episode's opening joins it; otherwise the open episode closes, candidates published more than 90 days before the signal are dropped and the signal becomes a candidate; when the candidates hold two independent participants (COR-017) they open an episode at this signal's `published_date` (`episode_opened_at`) and the candidate list is emptied. Each episode is one live row of `corroboration` with `entity_key`, `ticker` (empty for the entity scope), `participants_hash` (a hash of the sorted participant `event_id`s), `participant_event_ids`, `distinct_source_count`, `corroborated_at` (the latest participant `published_date`), `episode_opened_at`, `first_detected_at`, `excluded_reason`, `published_at` and `superseded_by`; the table enforces `episode_opened_at <= corroborated_at <= first_detected_at`. A scan reconciles every entity it touches against its episodes: an episode without a row is inserted, a superseded row an episode produces again is made live, a live row no episode produces is superseded by the `participants_hash` of the episode in its scope that shares a participant with it or by the literal `rules`, and `excluded_reason` follows the rules. Superseded rows are kept and are left out of notifications and REST responses.
- <a id="COR-019"></a>**COR-019** — For each ticker carried by a company that an entity's eligible signals mention, the scan builds the episodes of that ticker's scope, the entity's signals that mention a company carrying it, and stores them as rows with that `ticker`. A ticker record exists only when two independent sources on the entity both name the company within the window, and opens at the publication of the second; a broad entity, and a company named by one participant, get none.
- <a id="COR-020"></a>**COR-020** — `corroboration_rules_state` holds the rules hash core-hub last applied. On start, when it differs from the file's, the rules sync sets `corroboration_key` on every `GeneTarget` and `Mechanism` node, then marks every `Signal` pending with a fresh write token, in batches of `corroboration.rules-sync-batch-size`, and stores the hash last, so a sync that failed runs again in full. A scan does nothing while the stored hash differs from the rules in force.

## Rationale

Non-normative.

- **Why episodes** (COR-018). Grouping per pending signal left groups on a busy entity overlapping without nesting, so they were never superseded: one entity held 101 live rows. An episode opens on the signal that completes the first independent pair and accepts joiners for one window, so every participant lies within the window of the opening signal, a continuous flow re-opens only on fresh evidence, and the result is a function of publication dates alone. A chain (each signal within the window of the next) would never close on a busy entity.
- **Why ticker scopes** (COR-019). A ticker list on the entity record would date the ticker by the entity's opening, before the second company-naming source was public. A ticker scope gives each ticker its own opening.
- **Known limits.** A ticker is today's SEC mapping (HUB-034); a same-finding match needs titles and catches only the source-type pairs the rules file lists.
- **The score depends on the run date** (COR-013). Its recency term uses the service clock, so a historical corroboration scores differently each day. `specs/company-program-corroboration.md` proposes an `as_of` parameter that would fix it; until that merges, COR-013 describes today's behaviour.
- **Published corroborations are never withdrawn.** A superseded record stays published; consumers deduplicate and read the larger group when it arrives.

## Known traps

Sources: `services/core-hub/CLAUDE.md:41`, `CLAUDE.md:155`.

- **Two contract tests still carry the dropped watermark's name**: `test_watermark_advances_and_is_not_reprocessed` and `signalIngestedInTheWatermarkSecondIsCorroborated`. They test the pending-signal scan (COR-012, COR-011); renaming them is a code change for a fix spec.
- **Never inline the contract test's cases into a concrete test.** A second implementation must pass the abstract class as it is (COR-001).
