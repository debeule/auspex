# Corroboration

## Scope

How core-hub finds corroborations: the `CorroborationService` extension point and its contract test, the definition, the only corroboration kind, the record and its supersession, the pending-signal scan, the publication of new records, the score, and the scan's failure counter.

Not in this file: the shape, versioning and delivery identity of the published `CorroboratedSignalEvent` (CON-032 to CON-034 in [contracts.md](../system/contracts.md)); the graph the scan reads ([storage.md](storage.md)); how REST responses present corroborations ([http-api.md](http-api.md)); the quality gate on sampled corroborations, which [extraction.md](../ingestion/extraction.md) owns; metric names ([observability.md](../operations/observability.md)).

## Requirements

- <a id="COR-001"></a>**COR-001** — All corroboration sits behind `CorroborationService` (applies INV-5). Every implementation extends the abstract `CorroborationServiceContractTest` and passes it unmodified; the test's helpers write signals as the write path does, pending with a write token (COR-008).
- <a id="COR-002"></a>**COR-002** — The implementation is `ScheduledCorroborationService`, a scan of the graph on a fixed delay set in configuration (`corroboration.interval-ms`). A stream-processing implementation is not a requirement; one would replace this one behind the same interface.
- <a id="COR-003"></a>**COR-003** — Two signals corroborate when they reach the same entity node through `TARGETS` or `USES_MECHANISM`, never `MENTIONS`, come from different `source_type`s, and were published at most 90 days apart, both ends included. The window is measured between the two signals' `published_date`s, never against the current time.
- <a id="COR-004"></a>**COR-004** — The only corroboration kind is shared-entity corroboration over `GeneTarget` and `Mechanism` nodes. Its `entity_key` is the entity's normalized name, a colon, and the node label, for example `BCL11A:GeneTarget`. A new kind is a change to this requirement, made by the spec that adds it.
- <a id="COR-005"></a>**COR-005** — A corroboration record is one row per entity per participant set: `entity_key`, `participants_hash` (a hash of the sorted participant `event_id`s), `participant_event_ids`, `distinct_source_count`, and `corroborated_at`, the latest participant `published_date`. `corroborated_at` is the only field a backtest joins on.
- <a id="COR-006"></a>**COR-006** — A record's `first_detected_at` is the time of the scan that wrote it and is diagnostic only; nothing joins or filters on it.
- <a id="COR-007"></a>**COR-007** — When a larger group containing all of a record's participants is written for the same entity, the smaller record's `superseded_by` is set. Superseded records are kept, and are left out of notifications and REST responses.
- <a id="COR-008"></a>**COR-008** — Every graph write of a signal marks it pending (`corroboration_pending`) with a fresh `write_token`, in the write's own transaction.
- <a id="COR-009"></a>**COR-009** — A scan reads at most one batch of pending signals (`corroboration.scan-batch-size` in `application.yml`) and matches each against the signals on its entities whose `published_date` lies within 90 days of its own. An entity with more signals than the degree cap (`corroboration.degree-cap`, default 500) is skipped.
- <a id="COR-010"></a>**COR-010** — A scan's inserts commit only after every event it sends is acknowledged; the pending flags it read are cleared after that commit, and only on signals whose write token is still the one the scan read. A failed send, commit or clear leaves the signals pending for the next scan.
- <a id="COR-011"></a>**COR-011** — No clock decides which signals a scan sees: a write that commits late, a lagging partition, a dead-letter replay and a re-extraction are all scanned once committed. A wall-clock filter may narrow the candidates only as a documented optimization, never as the definition.
- <a id="COR-012"></a>**COR-012** — Each new record that is not superseded is published once, by the scan that inserts it, to `auspex.signals.corroborated`, keyed by `entity_key`; a group already recorded is not published again. A commit that fails after its sends were acknowledged sends the event again on the next scan, so delivery is at-least-once (CON-033).
- <a id="COR-013"></a>**COR-013** — A corroboration's score is `0.7 × diversity + 0.3 × recency`, clamped to [0, 1], where `diversity = min(1, (distinct_source_count − 1) / 4)` and `recency` falls linearly from 1 at `corroborated_at` to 0 ninety days later. The score is computed when it is read, against the service clock, and is never stored or published.
- <a id="COR-014"></a>**COR-014** — Every failed run, whether the scan, a send or the clear failed, increments the scan-failure counter, whose name is in [observability.md](../operations/observability.md).

## Rationale

Non-normative.

- **Why a participant hash** (requirements §4.1). Keying a record on its participant ids makes a second record appear whenever a fourth signal joins a group: duplicate notifications and double-counted backtest observations. One row per participant set, with supersession, keeps one live record per entity.
- **The score depends on the run date** (COR-013). Its recency term uses the service clock, so a historical corroboration scores differently each day. `specs/company-program-corroboration.md` proposes an `as_of` parameter that would fix it; until that merges, COR-013 describes today's behaviour.
- **Published corroborations are never withdrawn.** A superseded record stays published; consumers deduplicate and read the larger group when it arrives.

## Known traps

Sources: `services/core-hub/CLAUDE.md:41`, `CLAUDE.md:155`.

- **Two contract tests still carry the dropped watermark's name**: `test_watermark_advances_and_is_not_reprocessed` and `signalIngestedInTheWatermarkSecondIsCorroborated`. They test the pending-signal scan (COR-012, COR-011); renaming them is a code change for a fix spec.
- **Never inline the contract test's cases into a concrete test.** A second implementation must pass the abstract class as it is (COR-001).
